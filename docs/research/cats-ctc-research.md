## 1. Design vs. Operation Split (`designer` vs. `cats` vs. `TrainStat`)

CATS is structured as a suite of three standalone Java programs that share data via XML files and TCP sockets (`catsManual §1, pp. 2–3`; `DesignerManual §1, p. 4`; `DesignerManual §15, pp. 107–111`):

| Program | Role | JMRI Dependency | Entry Point & Artifacts |
| :--- | :--- | :--- | :--- |
| **`designer`** (`designer.jar`) | Offline CAD-style tile-grid panel editor and hardware/signal/operations configuration tool. | **None** at runtime (requires only Java 1.8+ and `jdom2.jar` for XML parsing; `DesignerManual §3, p. 9`). | `designer.gui.Ctc` (`DesignerManual §17.6, p. 117`). Outputs a self-contained `.xml` layout description file (`<DOCUMENT>`). |
| **`cats`** (`cats.jar`) | Runtime Digicon-inspired CRT dispatcher panel, interlocking/route engine, and vital signal logic solver. | **Runs inside JMRI** as a custom JMRI application (`LaunchJMRI.exe cats.apps.Crandic`; `catsManual §8.10, p. 59`). | Loads the `.xml` file generated by `designer`, instantiates JMRI devices (`Sensor`, `Turnout`, `SignalHead`, `SignalMast`, etc.), and runs the live session. |
| **`TrainStat`** (`TrainStat.jar`) | Optional networked tabular status display and crew-assignment terminal for yardmasters and trainmasters. | **None** (connects to CATS over TCP/IP, default port `54321`; `DesignerManual §15.1, p. 108`). | Reads/updates CATS `TRAINSTORE`, `CREWSTORE`, and `JOBSTORE` records over the network. |

### 1.1 Why `designer` Is Separated from `cats`
1. **Strict Authoring vs. Operating Separation**: In `designer`, the layout owner draws the track schematic on a 2D spreadsheet-like grid, defines block boundaries, places signal icons, creates signal aspect templates, binds JMRI addresses, and defines default train/crew/job lineups (`DesignerManual §4–§12, pp. 10–75`). None of the track topology, block boundaries, or signal templates can be edited inside `cats` during an operating session (`catsManual §3.3, p. 15`).
2. **Offline Portability**: Because `designer.jar` only depends on `jdom2.jar` and standard Java Swing, a layout owner can edit the layout XML file on any computer without installing JMRI or configuring layout hardware connections (`DesignerManual §3, p. 9`).
3. **Single Self-Contained XML Artifact (with Optional JMRI Panel Include)**:
   - `designer` serializes the entire design—fonts (`<FONTDEFINITION>`), colors (`<COLORDEFINITION>`), timing counters (`<COUNTER>`), signal templates (`<SIGNALTEMPLATE>`), train/job/crew tables (`<TRAINSTORE>`, `<JOBSTORE>`, `<CREWSTORE>`), JMRI prefix mappings (`<JMRINAME>`), and the 2D `<TRACKPLAN>` of `<SECTION X="..." Y="...">` grid tiles—into a single `.xml` file (`RMR_Full.xml (1-250)`).
   - Optionally, `Appearance -> Include File` (`DesignerManual §14.1.19, p. 91`) embeds a reference to a JMRI PanelPro XML file so `cats` will auto-load JMRI tables/Logix at startup, though the manual warns of race conditions where `cats` initializes before JMRI finishes loading the included file.
4. **Runtime Compilation of Topology into Logic**: When `cats` opens the XML file (`catsManual §3.2, p. 14`), it does **not** load pre-compiled boolean equations from the XML. Instead, `cats` walks the `<SECTION>` and `<SEC_EDGE>` objects from the XML, binds adjacent grid edges (`SecEdge.bind()`), welds contiguous track segments into `TrackSequence`s and `Block`s, and dynamically instantiates the parallel GUI (`TrackEdge`) and simulated field (`BasicVitalLogic`, `FieldSignal`, `TrackCircuit`) object graphs in memory (`EdgesDesign8.docx, pp. 11–14, 54–55`).

## 2. Domain Abstractions in CATS

### 2.1 Grids, Tiles (`Section`), Track Segments (`Track`), and Edges (`SecEdge`)
CATS models the railroad through the lens of its **dispatcher panel grid** (`DesignerManual §4, pp. 10–11`; `EdgesDesign8.docx, pp. 5–7, 11–14`):
- **Grid & `Section` (Tile)**: The canvas is a 2D rectangular array of square cells (`COLUMNS` × `ROWS`), fixed at 20×20 pixels at base scale (`catsManual §3.3.3, p. 20`). In both `designer` and `cats`, each grid cell is a `Section` (`designer.layout.items.Section`, `cats.layout.items.Section`) addressed by `(X, Y)` coordinates (`RMR_Full.xml:113`).
- **`Track` (Track Segment)**: Inside a `Section`, a track segment is a straight line connecting two of the cell's four edges (`RIGHT`, `BOTTOM`, `LEFT`, `TOP`). Because a cell has 4 edges, there are exactly $\binom{4}{2} = 6$ possible track segment orientations per cell (`HORIZONTAL`, `VERTICAL`, `UPPERSLASH`, `LOWERSLASH`, `UPPERBACKSLASH`, `LOWERBACKSLASH`; `DesignerManual §6.1, p. 13`; `RMR_Full.xml:126-193`). No curves exist inside a cell; diagonals provide 45° transitions. Multiple segments can coexist in one cell (`<TRACKGROUP>`) to form turnouts, crossings, or parallel diagonal tracks.
- **`SecEdge` (Section Edge)**: Every `Track` segment terminates on two cell edges. The intersection of a track end and a cell boundary is a `SecEdge` (`EdgesDesign8.docx, p. 5`):
  - **Peers**: The two `SecEdge`s at opposite ends of the same `Track` segment inside a cell are `Peer`s.
  - **Neighbors (`Joint`)**: When two cells touch (or are logically linked across the screen via unchecking *"Joins to adjacent track"* to create a `<SHARED X="..." Y="...">` "hyper-jump" for flyovers or continuous loops without drawing a literal loop on screen; `DesignerManual §9, pp. 37–38`; `RMR_Full.xml:140`), their touching `SecEdge`s are `Neighbor`s.
- **CATS 3 `TrackEdge` Hierarchy (`EdgesDesign8.docx, pp. 6–7`; `cats/layout/items/`)**:
  In CATS 3, Rodney Black refactored the edge model so contiguous non-branching `SecEdge`s are "welded" into a `TrackSequence` bounded by specialized `TrackEdge` subclasses:
  - `PtsEdge` and `FrogEdge`: Represent the points end and frog legs of a turnout.
  - `BlkEdge`: Marks an insulated joint / detection block boundary (`BLOCK` in XML).
  - `IntermediateEdge` (extends `BlkEdge`): A block boundary with a physical wayside signal (`PHYSIGNAL`) but **no** panel icon (`PANELSIGNAL`).
  - `CPEdge` (extends `IntermediateEdge`): A block boundary with a dispatcher `PANELSIGNAL` icon (an absolute signal / Control Point / APB Head Block).
  - `InternalXEdge`, `XEdge`, `XBlkEdge`: Specialized edges for diamonds (track crossings) inside a cell or on a cell boundary (`DesignerManual §9.5.3, pp. 60–65`).

### 2.2 Track Speeds
Each `Track` segment has a speed attribute (`Default`, `Normal`, `Limited`, `Medium`, `Slow`; `DesignerManual §6.1, p. 13`).
- When set to `Default`, straight/through tracks and the `Normal` leg of a turnout default to `Normal` speed, while diverging legs of a turnout automatically default to `Medium` speed (`DesignerManual §6.1, p. 13`; `§17.4, p. 116`).
- CATS uses these four track speeds as the sole mechanism for both **speed signaling** and **route signaling**—in route signaling, `Medium` (or `Limited`/`Slow`) is simply used as a proxy flag for a diverging route (`DesignerManual §8.1.1, p. 24`; `NewDesign.doc, pp. 4–6, 44–48`).

### 2.3 Detection Blocks (`Block`), Occupancy Sensors (`Detector`), and Reporters
- **Topological Definition of a Block**: A detection `Block` (`cats.layout.items.Block`) is defined as the maximal connected set of `Track` segments reachable without crossing a `BlkEdge` (block boundary) (`DesignerManual §4, p. 11`; `§9, p. 36`). Every `Track` segment in `designer` **must** belong to a named `Block`; otherwise `designer` paints it in `ERROR` red and `cats` will either omit it or crash (`DesignerManual §6.3, p. 14`; `§9.1.2, p. 41`).
- **Constraint on Block Boundaries and Switch Points**: A cell edge that contains switch points (`PtsEdge`) **cannot** simultaneously be a block boundary (`BlkEdge`), nor can the mating edge in the adjacent cell be a block boundary, because `cats` cannot visually draw both a block gap and switch points on the same edge (`DesignerManual §9, p. 37, fn. 12`). Consequently, an OS (Over-Switch) section or turnout must have an extra track segment or place its block boundary on an adjacent non-point edge.
- **Normal, Dark, and Hidden Blocks (`DesignerManual §9.1.2, pp. 41–42`)**:
  - **Normal Block**: Has a name, `VISIBLE="true"`, and at least one occupancy detector (`OCCUPIEDSPEC`/`UNOCCUPIEDSPEC`). Drawn in `Block Empty` (white) in `designer`.
  - **Dark Block**: Has a name and `VISIBLE="true"`, but **no** occupancy detector defined. Drawn in `Dark` (grey) in `designer` and `cats`. Used for dark territory, unbonded sidings, or magnet-board operation (`DesignerManual §6.3, p. 15`). Placing a train label on a dark block manually forces occupancy color (`catsManual §4.3.2, p. 48`).
  - **Hidden Block**: Has `Show Block` unchecked (`VISIBLE="false"`). Not drawn on the dispatcher panel, but participates in CATS logic (e.g., hidden staging leads with ABS signals or computer-controlled staging ladders; `DesignerManual §9.1.2, p. 41`).
- **Occupancy Detectors & Debounce Filters**:
  - Each block defines an `Occupied Report` (`<OCCUPIEDSPEC>`) and `Unoccupied Report` (`<UNOCCUPIEDSPEC>`). If only one is entered, CATS 3 automatically synthesizes the other using the opposite polarity (`Throw` vs. `Close`) (`DesignerManual §9.1.3, p. 42`).
  - Because model railroad wheel/rail detection often flickers or produces phantom spikes (e.g., BDL162 silent-drive spikes or dirty track dropouts), CATS includes global `Occupancy Debounce` and `Unoccupancy Debounce` timers (`cats.layout.OccupancyFilterCounter`) plus a 12-bucket `Occupancy Duration` spectrum analyzer (`cats.layout.OccupancySpectrum`) that logs sub-second glitches to JMRI `Memory` variables `IMDECODER_ACTIVE_1..5` and `IMDECODER_INACTIVE_1..5` (`catsManual §3.3.8–§3.3.9, pp. 21–23`; `EdgesDesign8.docx, pp. 92–93`).
- **Stations & Train Reporters**:
  - A `Block` can optionally specify a `Station` name (for TrainStat reporting, JMRI Operations location sync, and multi-desk CATS train handoffs; `DesignerManual §9.1.4, p. 42`) and a JMRI `Reporter` (`<REPORTERSPEC>`) for Digitrax Transponding / RFID / RailCom train-label positioning (`DesignerManual §9.1.5, pp. 42–43`).

### 2.4 Turnouts (`SwitchPoints`), Feedback Modes, and Lock Taxonomy
When two or more `Track` segments in a `Section` terminate on the same edge, `designer` recognizes that edge as switch points (`SwitchPoints`, `PtsEdge` / `FrogEdge`), unless disambiguated as a boundary crossing (`DesignerManual §9.5, pp. 55–65`):
- **Anonymous Coordinate Identity**: Notably, **turnouts in CATS do not have names**; they are identified solely by their grid coordinates `(X, Y)` and edge in `designer` and in the `Points Table` / `Routes Table` (`DesignerManual §8.4.3–§8.4.4, pp. 34–35`).
- **Mandatory `Normal` Route**: Every `SwitchPoints` must have exactly one leg checked as the `Normal Route` (`NORMAL="true"`), or `designer` paints the turnout in red `ERROR` color and `cats` will crash (`DesignerManual §9.5, p. 55`).
- **`Spur` Checkbox (Dispatcher vs. Local Control)**:
  - If `Spur` is **unchecked** (`SPUR="false"`), the turnout is an OS section / Control Point switch (`OSEdge`) and the dispatcher can throw it by left-clicking its grid tile (`DesignerManual §9.5, p. 55`).
  - If `Spur` is **checked** (`SPUR="true"`), the dispatcher cannot throw the turnout from the panel (`catsManual §8.7, p. 57`), and N/X routing will only traverse its `Normal` alignment (`catsManual §4.2.2, p. 41`).
- **Per-Turnout and Per-Leg Decoder Bindings (`DesignerManual §9.5.1–§9.5.2, pp. 56–60`)**:
  - **Turnout-Wide (Electric Lock / Local Control)**:
    1. `Turn Locked Light On`: Command sent when CATS locks the turnout against field control.
    2. `Turn Unlocked Light On`: Command sent when CATS unlocks the turnout for local crew use (when Track Authority is granted).
    3. `Turnout Unlocked Report`: Input sensor from the field reporting that a trainman has unlocked a switch padlock / electric lock (`SWITCHUNLOCK`), which paints an `Unlocked Icon` (`U`) on the panel and drops protecting signals to Stop.
    4. `Turnout Locked Report`: Input sensor reporting the switch lock has been restored.
  - **Per-Route Leg (`<ROUTEINFO ROUTEID="...">`)**:
    1. `Select Route Command`: Output command(s) (or `Chain`) sent to throw the switch motor to this leg.
    2. `Select Route Request`: Input from a fascia pushbutton ("fly-by-wire" / control-by-request) asking CATS to validate safety and throw the points on the crew's behalf. If the same pushbutton address is entered on both legs, CATS treats it as a toggle button (`DesignerManual §9.5.2, p. 57`).
    3. `Route Selected Report`: Feedback input confirming points are locked in this alignment ("make").
    4. `Route Unselected Report`: Feedback input reporting points have left this alignment ("break").
- **Three Turnout Feedback Regimes (`DesignerManual §9.5.2, pp. 56–58`; `EdgesDesign8.docx, p. 107`)**:
  1. *No Feedback*: Neither report is defined (or `Route Selected Report` echoes `Select Route Command`). Panel alignment updates instantaneously.
  2. *Positive Feedback*: Only `Route Selected Report` is defined on each leg (e.g., one SPDT microswitch or Tortoise contact).
  3. *Exact Feedback*: Both `Route Selected Report` and `Route Unselected Report` are defined on all legs (two sensors). While points are in transit (`CurrentRoute == OutofCorrespondence`), the panel shows a gap at both frogs until the "make" report arrives.

### 2.5 Signals: `PanelSignal` vs. `PhysicalSignal`, `SignalHead` vs. `SignalMast`, and Aspect Templates
CATS separates a signal's presence on the dispatcher screen from its physical existence on the layout (`DesignerManual §9.2.1, pp. 43–52`):

#### A. Four Signal Classifications (`Table 3: Signal Types`, `DesignerManual §9.2.1, p. 47`)
At any block boundary (`BlkEdge`), two checkboxes—`Layout Signal Type` (`<PHYSIGNAL>`) and `Panel` (`<PANELSIGNAL>`)—define four combinations:
1. **Control Point (`Layout` checked, `Panel` checked -> `CPEdge`, `CPVitalLogic`)**: An absolute signal (or APB Head Block) with both a physical mast on the layout and an icon on the dispatcher panel. CTC routes originate and terminate at Control Points.
2. **Intermediate Signal (`Layout` checked, `Panel` unchecked -> `IntermediateEdge`, `IntermediateVitalLogic`)**: A permissive wayside signal on the layout that has **no** icon on the CATS dispatcher screen (shown only as a small filled dot in `designer`; `DesignerManual Figure 26, p. 49`). Propagates routes and spaces following trains.
3. **Place Holder (`Layout` unchecked, `Panel` checked -> `CPEdge` with `PhysicalSignal == null`)**: A virtual panel signal icon with no physical signal on the layout (painted in `No Physical Signal` grey when idle so the dispatcher knows the engineer has no wayside mast; `catsManual §4.2.1, p. 39`). Used for magnet boards, DTC/TWC boundaries, or subdividing staging tracks.
4. **No Signal (`Layout` unchecked, `Panel` unchecked -> `BlkEdge`, `BlkVitalLogic`)**: An unsignaled block boundary (e.g., an OS boundary or simple detection gap).

#### B. Signal Templates & The 2D Speed-Matrix Aspect Engine (`DesignerManual §8.1.1, pp. 20–26`; `cats/layout/AspectMap.java`)
Instead of requiring users to write per-signal boolean equations, CATS uses reusable **Signal Templates** (`<SIGNALTEMPLATE>`):
- A template specifies `TEMPLATEKIND` (`Lamp` or `Semaphore`), `TEMPLATEHEADS` (1, 2, or 3 heads/arms), and four behavioral flags: `Approach Lighting`, `Advance` (4-aspect / 3-block lookahead), `Speed Signals` (vs. Route Signals), and `Hold Only` (`AspectMap.java:106-126`).
- Internally, CATS defines **30 fixed indication slots** (`AspectMap.IndicationNames`, indices `0..29`, plus internal pseudo-indices `30 = TUMBLEDOWN` and `31 = OPPOSING`; `AspectMap.java:187-248, 469-484`).
- The template table (`DesignerManual Figure 7, p. 21`) is a 2D matrix where:
  - **Rows** are the **Protected Speed** (the slowest `Track` speed between this signal and the next signal in the direction of travel: `Normal`, `Limited`, `Medium`, `Slow`).
  - **Columns** are the **Next Speed / Next Signal State** (`Normal`, `Limited`, `Medium`, `Slow`, `None` [Restricting / end of track / unbonded], `Advance` [next signal showing Approach], and `Halt` [next signal at Stop or Stop & Proceed]).
  - **Bottom Override Cells**: `ARA 292 - Stop` (`R292`) for hazards/occupied/held, and `R291 - Stop and Proceed` (`R291`) for Track Authority / Maintenance lock (`DesignerManual §8.1.1, p. 22`).
- **6-Level Priority Evaluation (`DesignerManual §8.1.1, p. 22`; `FieldSignal.determineIndication()`, lines 190–250)**:
  1. **Priority 1 (`R291` / Restricting override)**: Dispatcher granted Track Authority, Out of Service, or Call-On.
  2. **Priority 2 (`R292` - Stop)**: Safety checks found a hazard (`DETECTIONLOCK`, `CONFLICTINGSIGNALLOCK`, `HOLDLOCK`, `SWITCHUNLOCK`, `TIMELOCK`, `ROUTELOCK`, `PROTECTIONLOCK`, `EXTERNALLOCK`; `LogicLocks.java:148-156`).
  3. **Priority 3 (`None` column - Restricting by speed)**: No next signal (end of track or entering an `UNDEFINED`/unbonded block).
  4. **Priority 4 (`Halt` column - Approach by speed)**: Next signal is showing Stop (`R292`) or Stop & Proceed (`R291`).
  5. **Priority 5 (`Advance` column)**: Template has `Advance` checked and next signal is showing an Approach indication.
  6. **Priority 6 (`Normal`/`Limited`/`Medium`/`Slow` columns)**: Next signal is showing a clear/proceed aspect; looks up `(MySpeed, NextSpeed)` in `AspectMap` (`SpeedTable` or `RouteProgressionMap`).
- For each cell in the template, the user selects the head appearance (`green`, `yellow`, `red`, `flashing green`, `flashing yellow`, `flashing red`, `lunar`, `flashing lunar`, `off`, or semaphore `vertical`, `diagonal`, `horizontal`; `PhysicalSignal.java:111-124`) for Head 0, Head 1, and Head 2.

#### C. Three-Tier JMRI Signal Realization: Bulb vs. `SignalHead` vs. `SignalMast` (`DesignerManual §9.2.1, pp. 44–46`; `§14.8, pp. 99–105`)
CATS supports three levels of hardware abstraction for driving signals (`PhysicalSignal.java`, `SWSignalHead.java`, `HWSignalHead.java`, `CatsSignalSystem.java`):
1. **"Bulb Signaling" (Discrete Binary Decoders in Designer)**: The user fills in `IOSpec` commands (`Throw`/`Close` on `LT`, `CT`, `LS`, etc.) for each color/position of each head directly in `designer` (`Figure 27, p. 50`), with checkboxes for `Off Command?` (`EXIT_CMD="true"`, sending the opposite command to extinguish the old lamp before lighting the new one) and `Software Flashing` (`SWSignalHead` using a `javax.swing.Timer` vs. `HWSignalHead` where hardware flashes the LED). At runtime, CATS wraps these into custom `cats.jmri.SWSignalHead` / `HWSignalHead` beans (`CATS:SignalHead:N`), synthesizes a `CatsSignalSystem` (`CATS1`, `CATS2`, ...) and `CatsAppearanceMap`, and registers a JMRI `SignalHeadSignalMast` (`IF$shsm:CATS1:template($1)`) (`PhysicalSignal.java:624-702`).
2. **"Aspect Signaling" (JMRI `SignalHead` by User Name)**: The user defines `SignalHead`s in JMRI PanelPro (e.g., Digitrax SE8C 4-Aspect or Grapevine) and enters only the JMRI `SignalHead` `User Name` in `designer`'s head tab (`DesignerManual §9.2.1, p. 50`; `§14.8, p. 99`).
3. **"Indication Signaling" (JMRI `SignalMast` by User Name, plus `Hold Only` Mode)**: The user defines a full `SignalMast` in JMRI PanelPro (e.g., DCC Signal Decoder, OpenLCB/LCC mast) and enters its `User Name` as the CATS signal `Name` with no head details (`DesignerManual §9.2.1, p. 46`; `§14.8, p. 101`).
   - If **`Hold Only`** is checked on the template (`DesignerManual §8.1.1, p. 26`; `PhysicalSignal.java:409-411`), CATS bypasses its own aspect solver and calls `EmbeddedMast.setHeld(rule == AspectMap.STOP_INDEX)`, allowing autonomous field hardware (such as LCC nodes running ABS/APB logic) to compute the aspect while CATS acts only as the CTC office hold/release and listens to `PropertyChangeEvent("Aspect")` to color the panel icon (`PhysicalSignal.java:889-896`).

### 2.6 Operating Regimes / Control Disciplines (`Discipline.java`)
Each `Block` is assigned one of five control disciplines (`DesignerManual §9.1.1, pp. 39–41`; `cats/layout/Discipline.java`):
1. **`CTC` (Centralized Traffic Control)**:
   - All Control Point signals (`CPEdge`) are held at `Stop` (`LogicLocks.HOLDLOCK`) until the dispatcher lines a route (`CPVitalLogic.java:178-185`).
   - Intermediates (`IntermediateEdge`) inside a CTC block are also held at `Stop` when idle until a route's `ROUTELOCK` propagates through their neighbor and clears their `HOLDLOCK` (`EdgesDesign8.docx, pp. 32–33`, *Figure 27: Linkages - CTC with Hold*). (Rodney Black notes in `EdgesDesign8.docx, p. 31` that prototype CTC intermediates are actually APB and show permissive aspects when idle; to get prototype idle intermediates in CATS, the modeler must set the intermediate blocks between OS sections to `APB` while keeping the OS sections `CTC`; `DesignerManual §9.1.1, p. 41`.)
2. **`APB` (`APB-2` / `APB-3` — Absolute Permissive Block)**:
   - Signals default to permissive (`Clear` / `Approach`) based on track conditions without dispatcher intervention (`DesignerManual §9.1.1, p. 40`). (`APB-3` is an unimplemented alias for `APB-2`; `Discipline.java:106-111`.)
   - **Traffic Stick Relay (`cats.layout.TrafficStickRelay`) & Tumbledown**: Each block edge monitors the sequence of local vs. neighbor occupancy (`0000 -> 0001 -> 0011 -> 0111` state machine in `EdgesDesign8.docx, pp. 38–40`) to set a directional Traffic Stick (`ENTER` vs. `EXIT` vs. `NDT`). Opposing signals ahead of a train "tumble down" (`AspectMap.TUMBLEDOWN_INDEX` over `TrackCircuit`) all the way to the next opposing `CPEdge` (Head Block), preventing opposing trains from entering single track while allowing following trains to advance on `Stop -> Approach -> Clear` (`signals.pdf, p. 23`).
   - CATS also allows a dispatcher to manually click and reserve CTC-style routes through `APB` territory (`DesignerManual §9.2.1, p. 47`).
3. **`ABS` (Automatic Block Signaling)**:
   - Unidirectional safety overlay; ignores direction of travel (`TrafficStickRelay` is not used). Any occupied block or fouled switch sets its protecting signals in both directions to `Stop`, with `Approach` one block out. Dispatcher routes cannot originate in or propagate through `ABS` blocks (`DesignerManual §9.1.1, pp. 39–40`; `§14.4, p. 96`).
4. **`DTC` (Direct Train Control / Track Warrant Control)**:
   - Designed for dark/unsignaled territory or TWC/DTC districts (`DesignerManual §9.1.1, pp. 40–41`). The modeler places "Place Holder" panel signals (panel icon only, no physical layout signal). The dispatcher sets routes from station to station just like CTC, locking switches and conflicting routes. However, as the train occupies and vacates blocks, the vacated blocks do **not** release to `Block Empty` white; they turn `DTC Trail` yellow/orange (`LogicLocks` / `GuiLocks.WARRANT`), leaving a "breadcrumb trail" of the train's warrant limits until the dispatcher manually clicks the signal to cancel/roll up the warrant (`catsManual §4.2.6, p. 46`).
5. **`Unknown` (`Discipline.UNDEFINED` — Unbonded / Dark Yard Track)**:
   - Has no signal protection and blocks route propagation. Any signal lined into an `UNDEFINED` block displays `Restricting` (via the `None` column of the template; `DesignerManual §8.1.1, p. 24`; `§14.4, p. 96`).

### 2.7 Interlocking Routes, N/X, Stacking, Fleeting, and Call-On
CATS implements a rich dispatcher route engine in `cats.layout.ctc` and `cats.layout.items.CPEdge` (`catsManual §4.1–§4.2, pp. 37–47`; `EdgesDesign8.docx, pp. 55–90`):
- **Quick Route**: Left-clicking an idle `CPEdge` signal icon scans along the **current turnout alignments** up to the next `CPEdge` in the direction of travel (or end of track / `ABS` / `UNDEFINED` boundary). It never moves turnouts (`catsManual §4.2.1, p. 39`). As a train traverses and vacates blocks, CATS performs **sectional release ("roll-up")**, freeing each vacated block and turnout behind the train (`catsManual §4.1, p. 38, fn. 4`).
- **Extended (`N/X` — Entry/Exit) Route**: Right-clicking an entry `CPEdge` and selecting `Set N/X Route`, then left-clicking an exit `CPEdge`, builds a **Directed Acyclic Graph (DAG)** (`cats.layout.ctc.RouteCreator`, `RouteNode`, `RouteNodePts`) across all facing/trailing turnout branches between entry and exit (`EdgesDesign8.docx, pp. 75–78`). CATS scores every candidate path by three metrics:
  1. Zero blocking conditions (occupancy, conflicting route, Track Authority, OOS, unlocked switch).
  2. Maximum number of `Normal` turnout alignments (preferring main tracks over sidings).
  3. Minimum number of turnouts that must be thrown (`catsManual §4.2.2, pp. 40–41`).
  CATS then waits for `Turnout Safety Delay`, commands the required turnouts to throw, waits for turnout feedback, and chains Quick Routes across every intermediate `CPEdge`.
- **Stacked Routes (`cats.layout.ctc.StackOfRoutes`)**: If an N/X path is currently blocked (e.g., by an opposing train), the dispatcher can `Stack Route`. CATS stores the route's DAG in `StackOfRoutes` with a `java.util.BitSet` indexing every `TrackEdge` in the DAG (`EdgesDesign8.docx, p. 88`). Whenever a blocking lock clears on a watched edge, CATS checks stacked DAGs from oldest to newest; a newer stacked route is allowed to execute ahead of an older blocked route **if and only if** their `TrackEdge` `BitSet`s have an empty intersection (`catsManual §1.1, p. 8`; `§4.2.3, p. 44`).
- **Fleeting**: Automatically re-establishes a route after a train clears it (`catsManual §4.2.6, p. 46`).
- **Call-On (Return to Train)**: Temporarily overrides occupancy in the next block (when the immediate OS block is vacant, the approach block is occupied, and the block beyond the OS is occupied by a standing cut of cars) to display a `Restricting` aspect for one move (`catsManual §4.2.5, pp. 45–46`).

### 2.8 JMRI `System Name` vs. `User Name` and `IOSpec` Hardware Bindings
CATS delegates all layout bus communication to JMRI via `cats.layout.items.IOSpec` and `cats.jmri.JmriDevice` (`DesignerManual §8.3, pp. 31–32`; `§13.1, pp. 75–81`; `IOSpec.java`):
- **Unified Binary Facade (`IOSpec`)**: Whereas JMRI strictly separates `Sensor`s (inputs) and `Turnout`s (outputs), CATS wraps JMRI `Sensor` (`S`), `Turnout` (`T`), `Light` (`L`), `Memory` (`M`), `Reporter` (`R`), `Route` (`O`), and CATS's own `IOSpecChain` (`IC` — a delayed macro sequence of commands used for yard ladders / diode matrices; `DesignerManual §8.2, p. 28`) into a single binary abstraction (`Close` vs. `Throw`) that can be used interchangeably as **either an input or an output** (`DesignerManual §13.1.2, p. 80`; `IOSpec.java:294-331, 668-849`).
- **Three Addressing Forms (`DesignerManual §13.1, p. 76`)**:
  1. `JMRI System Prefix` + `Address` + `Polarity` (e.g., `LS` + `192` + `Throw` -> `LS192`).
  2. `User Name` + `JMRI Device Type` + `Polarity` (e.g., `Staging_1` + `Sensor` + `Close`), looking up an existing object defined in a JMRI PanelPro XML file.
  3. **Both** (`System Prefix` + `Address` + `User Name` + `Polarity`), in which case CATS asks JMRI to create the object with that `SystemName` and assign the `UserName` (`DesignerManual §9.2.1, p. 44`).
- **Metered Connections (`ML`, `MS`, `MT`)**: Because CATS can flood LocoNet during startup refreshes, ladder chains, or aspect changes, CATS provides a `MeteredConnection` queue (`cats/jmri/MeteredConnection.java`) controlled by the `Loconet Governor` and `Refresh Delay` counters (`DesignerManual §8.3, p. 32`; `§14.1.5, p. 88`).

## 3. What CATS Does Really Well

1. **Zero-Code Derivation of Interlocking & Signal Logic from Topology**:
   - In raw JMRI PanelPro, setting up full CTC requires building a Layout Editor panel (or Control Panel Editor icons), populating Turnout/Sensor/Block/SignalHead/SignalMast tables, configuring Simple Signal Logic (SSL) or Signal Mast Logic (SML), and writing hundreds of JMRI Logix/LogixNG conditionals or Jython scripts for route locking, approach/time locking, call-on, and fleeting (`CabooseClass.pdf, pp. 23–29`).
   - In CATS, **drawing the panel in `designer` *is* programming the interlocking**: CATS automatically infers block boundaries, facing/trailing point topology, safety zones, protection zones, APB traffic-stick directional logic, and CTC route locking directly from how track segments connect across grid edges (`https://cats4ctc.wikidot.com/`; `EdgesDesign8.docx, pp. 5–14`).
2. **Pragmatic Speed/Route Signal Template Matrix**:
   - By mapping `(Protected Speed × Next Speed / Advance / Halt / None)` to a 30-entry table (`AspectMap.java`) and letting diverging turnout legs default to `Medium` speed, CATS handles both eastern Speed Signaling (e.g., CROR, NORAC, NYC, PRR) and western Route Signaling (e.g., ATSF, BN, BNSF, UP, SP) through a single algorithm without requiring custom scripting (`DesignerManual §8.1.1, pp. 20–25`; `NewDesign.doc, pp. 4–48`).
   - Furthermore, `designer` greys out unused speed rows/columns based on the track speeds actually used on the layout, reducing configuration burden (`DesignerManual §8.1.1, p. 21`).
3. **Graceful "Panel That Grows" Evolution (Magnet Board -> APB -> Full CTC)**:
   - A layout owner can draw a track plan in `designer` with zero hardware addresses (`RMR_magnet.xml`, `ArmstrongMagnet.xml`) and immediately use `cats` during an operating session as an interactive **computer magnet board**—dragging train labels across dark blocks, throwing virtual switches, and logging OS times (`NMRA2018.pdf, pp. 56, 166–192`).
   - As hardware detectors, switch motors, and signals are wired under the layout over months or years, the owner incrementally adds `IOSpec` addresses in `designer` and can switch blocks between `APB` (for unattended open houses; `catsManual §5, pp. 51–53`) and `CTC` (for dispatched sessions) with a radio button (`DesignerManual §9.1.1, p. 40`).
4. **High-Value Dispatcher & Operations Ergonomics Out of the Box**:
   - **N/X (Entry/Exit) DAG Pathfinding & Priority Route Stacking**: Dispatchers get modern CAD features—automatic multi-CP turnout alignment, non-overlapping out-of-order route stack execution (`BitSet` intersection), fleeting, and call-on—with zero scripting (`catsManual §4.2.2–§4.2.6, pp. 40–46`).
   - **Train Tracking, Crew Callboard, Hog-Law Timers, and JMRI Operations Sync**: CATS tracks train symbols or lead engine numbers across occupancy blocks, syncs real-time train length/weight/car counts with JMRI `OperationsPro` when a train enters a `Station` (`DesignerManual §16, pp. 111–114`), monitors crew hours of service ("dead on the law"; `DesignerManual §12.1–§12.5, pp. 73–75`), broadcasts yardmaster tables to `TrainStat` clients, supports multi-desk dispatcher handoffs via shared `Station` blocks (`DesignerManual §15.4, pp. 109–111`), and logs timestamped operating sessions for playback or NMRA Chief Dispatcher AP qualification (`catsManual §3.10, p. 35`; `§6, pp. 53–55`).
5. **Hardware Wiring Agnosticism (`IOSpec` & `SWSignalHead`)**:
   - Unlike JMRI's built-in `SignalHead` types—which make rigid assumptions about how hardware is wired (e.g., requiring all outputs to be JMRI `Turnout`s, assuming `CLOSED` = off and `THROWN` = on, or assuming fixed Digitrax SE8C address groupings)—CATS's `IOSpec` and `SWSignalHead`/`HWSignalHead` let a modeler mix and match any JMRI device type (`Sensor`, `Turnout`, `Light`, `Memory`, `Chain`) and polarity for each individual lamp or semaphore position (`DesignerManual §13.1, p. 77`; `SWSignalHead.java:49-61`).

## 4. Limitations, Complexities, and Pain Points in CATS

### 4.1 Tile-Grid Editing Constraints and Visual/Geometric Quirks
1. **Rigid 4-Edge Square Tile Geometry**:
   - Because every `Section` is a 4-edged square supporting only 6 straight-line segments, complex junctions must be contorted across multiple grid cells (`DesignerManual §4, p. 10`; `§9.5.3, pp. 60–65`).
   - **Block Boundaries Cannot Coincide with Switch Points**: Because CATS cannot draw both a block gap and switch points on the same cell edge (`DesignerManual §9, p. 37, fn. 12`), modelers cannot place an insulated joint directly at the points of a turnout on the grid; they must insert extra spacer track segments or shift block boundaries, which often produces awkward visual geometry (`DesignerManual §14.2, Figures 56–58, pp. 92–94`) and requires special-case lock propagation for "toe-to-toe" (back-to-back) turnouts (`EdgesDesign8.docx, pp. 99–103, 111`).
2. **Word-Processor Auto-Wrapping and Column Compression**:
   - By default, `cats` does not preserve `designer`'s 2D proportions: it treats the grid like a word processor (`Automatic Wrapping` and `Compress Screen`), shrinking horizontal-only columns to half width and dynamically breaking/wrapping the track diagram into horizontal bands wherever the fewest tracks cross the right window margin (`DesignerManual §6.4, pp. 16–17`; `catsManual §3.1, p. 14`). While these can be unchecked, forcing a fixed multi-deck layout geometry requires manually breaking the linear track plan and wiring `<SHARED X="..." Y="...">` non-adjacent hyper-jumps by hand (`DesignerManual §9, pp. 37–38`; `§14.1.12, pp. 89–90`).
3. **Loops Crash CATS Unless Broken with `<SHARED>` Links**:
   - Drawing a continuous oval or loop of track directly on the 2D grid in `designer` is permitted by the editor, *"but CATS will crash trying to handle it"* (`DesignerManual §9, p. 37`). Loops also cause hazards in the N/X DAG search if not carefully bounded (`catsManual §4.2.2, p. 41`).
4. **Tile-Overflow Painting and Mouse Hit-Box Bugs**:
   - Signal icons and text labels frequently spill outside their 20×20 pixel `Section` tile into neighboring tiles. As Rodney Black documents in `EdgesDesign8.docx, pp. 144–145` (*Screen Painting* and *Mouse Click Identification*) and `catsManual §4.2.1, p. 39` / `§8.7, p. 57`:
     - When an adjacent tile repaints, it erases the overflowing portion of a neighbor's signal icon without repainting that neighbor, leaving half-erased icons on screen until a manual `Refresh Screen`.
     - Because mouse clicks are indexed by the grid tile `(X, Y)` containing the item's logical anchor, clicking the visible head of a signal icon that overflowed into an adjacent tile fails to register as a signal click (or worse, throws a turnout in that adjacent tile!).
     - Turnouts have no names in `designer` (`DesignerManual §8.4.3, p. 34`), so debugging or cross-referencing turnouts in tables requires hunting by raw `(X, Y)` grid coordinates.

### 4.2 Coupling Between Dispatcher Panel View and Vital Logic ("The Panel *Is* the Model")
1. **Conflation of Schematic Presentation with Physical Railroad Topology**:
   - In CATS, there is no separate topological trackplan vs. dispatcher panel layout. The dispatcher screen's 2D tile grid (`Section` / `SecEdge`) **is** the single source of truth from which both the GUI and the simulated field logic are instantiated (`EdgesDesign8.docx, pp. 11–14`).
   - Whether a wayside signal is an **Absolute Signal / Control Point** (`CPEdge`) or a **Permissive Intermediate Signal** (`IntermediateEdge`) is determined **solely by whether the `Panel` checkbox is checked** to draw an icon on the dispatcher screen (`DesignerManual §9.2.1, Table 3, p. 47`).
   - As a result, to stop a yard route from propagating through a yard throat (`DesignerManual §14.4, Figure 60, p. 96`), the modeler is forced to place a fake "dummy" (panel-only) signal icon on the dispatcher screen and "fix up" a custom signal template just to trick the route solver.
2. **Non-Prototype CTC Intermediate Signal Behavior by Default**:
   - Because CATS assigns discipline (`CTC`, `APB`, `ABS`) per `Block`, placing intermediate signals inside a `CTC` block causes CATS to apply `HOLDLOCK` to the intermediates so they display **Stop (Red)** whenever no CTC route is lined (`EdgesDesign8.docx, pp. 31–33`). As Rodney Black explicitly notes (`EdgesDesign8.docx, p. 31`), this is a model-railroading misconception: on the prototype, intermediates between CTC control points operate as APB signals (displaying Clear/Approach when idle) and only the Control Point home signals are held at Stop. To achieve prototype behavior in CATS, the modeler must manually configure OS blocks as `CTC` and intermediate blocks as `APB` (`DesignerManual §9.1.1, p. 41`).
3. **Unbalanced / Staggered Signals Problem**:
   - Because CATS ties `BlkVitalLogic` and `FieldSignal` to individual block-boundary edges (`SecEdge`), staggered or unpaired signals (where a signal in one direction has no opposing signal at the same insulated joint—universal at prototype OS control points where the three home signals stand outside the points/frogs) create overlapping `Safety Zone` and `Protection Zone` headaches (`EdgesDesign8.docx, pp. 8–11, 22–25`). Rodney Black devotes dozens of pages in `EdgesDesign8.docx` to working around unpaired signals and notes in his clinic (`signals.pdf, p. 26`) *"3. Pair up signals (detection)"*.
4. **Simulated Code Line Is Internal and Bypassed in Key Places**:
   - In CATS 3, Rodney Black introduced `cats.layout.codeLine.CodeLine`, `cats.layout.vitalLogic.*`, and `cats.trackCircuit.*` to mirror prototype Office ↔ Code Line ↔ Vital Logic ↔ Track Circuit separation (`EdgesDesign8.docx, pp. 11–22`).
   - However, both the GUI (`TrackEdge`, `GuiLocks`) and the `VitalLogic` (`BasicVitalLogic`, `LogicLocks`) run inside the **same desktop Java process** on the same `RREventManager` worker thread (`EdgesDesign8.docx, p. 143`), and the separation is leaky:
     - `CodeLine` passes direct Java object references (`BasicVitalLogic recipient`, `TrackEdge recipient`) rather than station/unit addresses (`CodeLine.java:18-20, 148-161`).
     - Occupancy detection (`DETECTIONLOCK`) actually flows **Hardware -> GUI `Block` -> `VitalLogic` -> `CodeLine` -> GUI `TrackEdge`** (`Codes.java:38-39`; `EdgesDesign8.docx, pp. 90–92`) so that dragging a train label on a dark block or clicking `Occupy Block` on the GUI menu stimulates `VitalLogic` identically to a hardware sensor.
     - Route safety scanning and N/X / Stacked Route turnout sequencing are performed in the **GUI layer** (`CPEdge`, `RouteCreator`, `GuiLocks`), not in `VitalLogic` (`EdgesDesign8.docx, pp. 53, 58`: *"On the prototype, the Vital Logic would provide a safety check. CATS does not do this because of the additional complexity introduced in the GUI. The GUI will perform the safety check."*).

### 4.3 Central Desktop JMRI Lock-In vs. Distributed Vital Field Units
1. **Total Runtime Dependence on a Central PC Running JMRI & CATS**:
   - Unless the layout owner uses autonomous external hardware (such as LCC nodes with CATS's `Hold Only` mode; `DesignerManual §8.1.1, p. 26`), **all** vital interlocking, turnout locking, APB traffic-stick relays, approach lighting, software signal flashing, and aspect resolution execute inside the single `cats` Java process on the desktop PC (`wiring13.pdf, pp. 188, 1334–1345`).
   - If the JMRI/CATS computer is not running—or while it is booting up—field signals, software-locked fascia pushbuttons (`Select Route Request`), and interlocking protections are dead (`DesignerManual §9.5.2, p. 60`).
2. **Startup Synchronization and JMRI Version Fragility**:
   - Because JMRI is event-driven and CATS listens for JMRI property changes, starting CATS and layout power in the wrong order leaves block occupancy and signals out of sync unless `Initial Refresh` is enabled, which floods the layout bus and requires the dispatcher to wait 20–30 seconds before touching the panel (`DesignerManual §14.1.15, p. 90`; `catsManual §3, p. 13`).
   - **JMRI Schema Crash Trap**: When CATS creates its own `SWSignalHead`/`HWSignalHead` (`CATS:SignalHead:N`) or `CatsSignalSystem` objects in JMRI's tables, **saving the JMRI SignalHead or SignalMast table from PanelPro corrupts the JMRI XML file**: when JMRI later tries to load that XML file without CATS's custom classes in its schema validator, JMRI *"will try to create a CATS SignalMast, which it doesn't know how to do and crash horribly"* (`DesignerManual §9.2.1, pp. 47, 50`; `SWSignalHead.java:23-30`).
   - **JMRI Version Treadmill**: Because CATS subclasses internal JMRI classes (`DefaultSignalHead`, `DefaultSignalSystem`, `SignalHeadSignalMast`, managers, and logging/XML jars), routine JMRI upgrades repeatedly break CATS binary compatibility, requiring 11 separate version-specific CATS zip packages on the downloads page (`https://cats4ctc.wikidot.com/main:downloads`; `catsManual §1.1, pp. 6–8`; `§8.4, p. 56`; `§8.8, p. 57`).
3. **Only Digicon CRT GUI Is Supported Out of the Box**:
   - CATS only implements the modern CRT/mouse GUI (`EdgesDesign8.docx, p. 43`: *"The machine is the interface between the dispatcher and the signaling system. It could be a mechanical machine (relay based logic), a graphics monitor (Graphical User Interface), or a graphics monitor drawing a mechanical machine. CATS implements only the GUI."*).
   - Driving a physical US&S or GRS CTC lever/code-button machine requires external JMRI Logix/Jython scripts bridged through JMRI `Reporter` packets (`CodeLine.sendToReporter()`, `CodeLine.java:163-176`).

### 4.4 Handling of Non-CTC Regimes, Local Fascia Panels, and Electric Locks
1. **No Native Timetable & Train Order (TT&TO), Rule 251, or Yard Limits Semantics**:
   - While Rodney Black's clinics discuss TT&TO, Train Order Boards, "Mother May I", and Yard Limits (`signals.pdf, pp. 13–15`; `wiring13.pdf, pp. 71–81`), CATS's `Discipline` enum (`Discipline.java:84-90`) only models `CTC`, `APB`, `ABS`, `DTC`, and `UNDEFINED`.
   - There is no first-class Train Order Signal appliance in CATS (a train-order board would have to be manually hacked as a generic `ButtonItem` on the panel or controlled outside CATS; `signals.pdf, pp. 13–14`; `DesignerManual §9.4, p. 54`).
   - There is no concept of **Rule 251 (Current of Traffic)** as a distinct regime that informs default signal/switch placement, nor **Rule 93 Yard Limits** (which must be approximated using `ABS` or `Unknown` blocks plus dummy panel signals and hand-tweaked templates; `DesignerManual §14.3–§14.4, pp. 94–96`).
2. **Awkward Local Fascia Control & "Countermand / Oscillating Turnout" Hacks**:
   - In prototype railroading (and in Codeline), local fascia panels, electric locks, and dual-control switch selectors are wired directly to the **field bungalow processor**, which mediates local crew requests against vital locking locally in the field.
   - Because CATS has no field processor, local crew turnout control in CTC territory must be wired in one of three ways (`DesignerManual §9.5.2, pp. 59–60`; `wiring13.pdf, pp. 930–1178`; `EdgesDesign8.docx, pp. 104–108`):
     1. **Hardware Lock Relay / Key Switch**: CATS sends a `Turn Unlocked Light On` command when the dispatcher grants `Track Authority` on the block, energizing a relay (or lighting a green LED next to a fascia key switch, as on Pat Lana's Crandic; `wiring13.pdf, pp. 1028–1125`) that enables the local fascia toggle.
     2. **Software "Fly-by-Wire" (`Select Route Request`)**: The fascia pushbutton does not connect to the switch motor; it sends a JMRI sensor input to the central CATS PC, which checks if Track Authority is active and sends `Select Route Command` back out over the bus. (Requires the central PC and CATS to be running even for local switching!)
     3. **"Countermand Lock" (`Reverse Local Operations`)**: If the fascia button or DCC throttle throws the stationary decoder directly, CATS watches for unexpected turnout feedback and **commands the turnout to throw back** (`DesignerManual §9.5.2, p. 60`; `§14.1.14, p. 90`).
        - As Rodney Black warns in both manuals (`DesignerManual §14.1.14, p. 90`; `catsManual §3.3.16, p. 28`) and in `EdgesDesign8.docx, pp. 105–107`, this countermand mechanism is notorious for **infinite turnout oscillation ("movement storms")** if two turnouts share a decoder address (e.g., a crossover) and `Lock Turnout Decoders` is not configured properly, or when command and feedback addresses differ and JMRI suppresses repeat commands to the same `KnownState`!
3. **Electric Locks Tied to Block-Wide "Track Authority" (`Stop and Proceed`)**:
   - In CATS, the dispatcher cannot simply unlock an individual electric-lock spur switch with prototype running-time / approach-release mediation. Instead, the dispatcher must right-click the enclosing detection block and grant **`Track Authority`** (`LocalControlLock` / `MAINTENANCELOCK`), which unlocks all turnouts in that block and sets the protecting signals to **`Stop and Proceed` (`R291` — flashing red on the Crandic)** rather than absolute `Stop` (`catsManual §4.3.4, p. 49`; `EdgesDesign8.docx, pp. 129–140`).

## 5. Summary Comparison: CATS vs. Codeline Architectural Goals

| Dimension | CATS (`designer` + `cats`) | Codeline (`CODELINE_ARCHITECTURE.md`) |
| :--- | :--- | :--- |
| **Primary Metaphor** | 1990s Digicon CRT Dispatcher Screen; **the 2D tile panel *is* the model**. | 4-Layer Railroad Engineering Stack (Layer 1 Office ↔ Interface A Code Line ↔ Layer 2 Vital AREMA Solver ↔ Interface B Smart Appliance ↔ Layer 3/4 Realization). |
| **Design vs. Runtime** | Offline `designer` (tile grid -> XML) + runtime `cats` (runs inside JMRI on central PC). | Live `FieldUnit-Studio` workshop with embedded real-time Layer 2 AREMA solver, virtual simulator, and firmware/config generator. |
| **Track & Topology Model** | 20×20px square `Section` tiles with 6 straight `Track` lines and 4 `SecEdge`s; points cannot share edges with block boundaries; loops crash unless broken with `<SHARED>`. | Continuous topological trackplan decoupled from dispatcher/wayside panel layouts; context-sensitive smart defaults per operating regime. |
| **Vital Logic Execution** | Simulated inside the central desktop Java/JMRI process (`cats.layout.vitalLogic`); route safety checks performed by the GUI layer. | True AREMA vital logic (`HR`, `DR`, `HSR`, `ASR`, `WLR`, `KR`, `TR`, `SR`) capable of running either in Studio simulation or compiled into distributed ESP32/Arduino field units. |
| **Code Line (Interface A)** | Internal in-memory Java queue (`CodeLine.java`) passing object pointers; bypassed by occupancy and GUI safety scans. | True plug-and-play positive-control protocol boundary (`829NWS, (829RWS)`); supports physical US&S/GRS machines, virtual panels, or automated test runners interchangeably. |
| **Signal Resolution** | 30-rule 2D speed matrix (`Protected Speed × Next Speed`) in `AspectMap.java`, mapped to head colors per `SignalTemplate`. | Era- and rulebook-aware AREMA solver: evaluates route operands (`H`/`D` lines, turnout speeds, correspondence) and caps to functional head position capabilities (`2/3/4-pos`). |
| **Local Panels & Electric Locks** | Mediated by central PC via block-wide `Track Authority` (`R291`), fly-by-wire requests, or countermand reversal (`Reverse Local Operations`). | Wired directly to the field processor (Layer 3/4) and mediated locally by vital electric-lock, running-time, and dual-control switch logic. |
| **Hardware Binding** | Bound inside the panel XML via JMRI `IOSpec` (`SystemName` / `UserName`) or custom `SWSignalHead` beans. | Cleanly separated below Interface B/C (Smart MQTT/JMRI appliances, animated C/MRI nodes, or Layer 4 composite wiring templates with Active-Low defaults). |
